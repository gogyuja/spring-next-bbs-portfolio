# AUTH-001 소셜 로그인/회원가입 설계 문서

**날짜:** 2026-06-11
**이슈:** #14
**범위:** 프로젝트 초기 셋업 + AUTH-001 BE + FE 구현

---

## 1. 개요

카카오·구글 소셜 계정으로 로그인. 최초 로그인 시 자동 회원가입 처리.
BE-driven OAuth 방식: Spring Security 6가 OAuth 전체 플로우를 담당.
OTC(One-Time Code)를 경유해 Access Token을 안전하게 전달한다.

---

## 2. 전체 아키텍처 & 데이터 플로우

```
[FE 로그인 페이지]
  카카오/구글 버튼 클릭
      ↓
GET  BE /oauth2/authorization/{provider}    ← Spring Security 처리
      ↓
소셜 로그인 페이지 (카카오/구글 서버)
      ↓
GET  BE /login/oauth2/code/{provider}       ← 소셜 콜백
      ↓
CustomOAuth2UserService
  - provider + provider_id 로 User 조회
  - 없으면 신규 생성 (닉네임: User-{UUID 앞 8자리})
  - 로그인 차단 여부 확인 → 차단 시 에러 리다이렉트
      ↓
OAuth2LoginSuccessHandler
  1. Access Token  생성 (30분, JWT)
  2. Refresh Token 생성 (7일, JWT)
     → Redis: SET RT:{userId}  {refreshToken}  EX 604800
  3. HttpOnly 쿠키: refresh_token, SameSite=Lax (로컬) / None;Secure (prod)
  4. OTC 생성 (UUID, 30초 TTL)
     → Redis: SET OTC:{code} {accessToken} EX 30
  5. 302 redirect → {FE_URL}/auth/callback?code={otcCode}
      ↓
[FE /auth/callback 페이지]
  - searchParams에서 code 추출
  - useAuth().exchangeToken(code) 호출 (useMutation 래퍼)
      ↓
[BE POST /api/auth/token]
  - Redis GETDEL OTC:{code} (원자적 조회+삭제)
  - 결과 null → 400 (코드 없음 또는 만료 — 재사용과 구분 불필요)
  - 결과 있음 → { success: true, data: { accessToken } }
      ↓
[FE /auth/callback 페이지]
  - 응답에서 accessToken 추출
  - Zustand AuthStore에 저장 (메모리)
  - router.replace('/')
```

### 토큰 전략

| 토큰 | 수명 | 저장 위치 |
|---|---|---|
| Access Token | 30분 | FE 메모리 (Zustand) |
| Refresh Token | 7일 | Redis + HttpOnly 쿠키 |
| OTC (One-Time Code) | 30초 | Redis (GETDEL로 원자적 1회 사용) |

### OTC 보안 설계

Access Token을 URL 쿼리 파라미터로 전달하면 브라우저 히스토리/서버 로그에 JWT가 노출된다.
OTC는 불투명한 코드만 URL에 포함하고, AT는 백채널(POST) 응답으로만 전달한다.
Redis `GETDEL` (Redis 6.2+, 이 프로젝트는 Redis 7)을 사용해 조회와 삭제를 원자적으로 처리한다.
재사용과 만료는 동일하게 `null` 반환이므로 에러 코드를 구분하지 않는다.

### 5.4 SecurityConfig

```
AUTH-001 범위에서의 URL 권한 설정:
  /oauth2/authorization/**          → permitAll
  /login/oauth2/code/**             → Spring Security OAuth2 처리
  /api/auth/**                      → permitAll
  /api/**                           → permitAll  ← JwtAuthFilter 없으므로 전체 허용
                                                    (authenticated 강제는 AUTH-002/003에서)

Session: STATELESS
CSRF: 비활성화 (STATELESS + SameSite=Lax + X-Requested-With 헤더로 대체)
CORS: FE origin 허용

oauth2Login:
  userInfoEndpoint → CustomOAuth2UserService
  successHandler   → OAuth2LoginSuccessHandler
  failureHandler   → OAuth2LoginFailureHandler

※ JwtAuthenticationFilter: AUTH-001 범위 밖.
  AUTH-002/003 구현 시 추가하며, 그 때 /api/** 를 authenticated로 전환한다.
```

**CSRF 대책:** STATELESS로 Spring CSRF 비활성화.
RT 쿠키는 SameSite=Lax로 크로스사이트 POST에서 자동 전송 차단.
향후 RT 사용 엔드포인트(reissue, logout)에 `X-Requested-With: XMLHttpRequest` 헤더 검증 추가(AUTH-002/003).

**운영 쿠키:** FE(Vercel)↔BE(EC2) 크로스 오리진이므로 prod에서는 `SameSite=None; Secure` 필요.
`application-prod.yml`에서 `cookie.secure=true`, `cookie.same-site=None`으로 프로파일 분리.

### 5.5 CustomOAuth2UserService

```
1. registrationId 추출 (kakao / google)
2. provider별 attribute 정규화 → OAuth2UserInfo
   카카오: kakao_account.profile.nickname, kakao_account.profile.profile_image_url
   구글:   name, picture, email
3. UserRepository.findByProviderAndProviderId()
4. 없으면 User.create():
   - nickname: "User-" + UUID.randomUUID().toString().replace("-","").substring(0, 8)
   - email: 소셜 제공 시 저장
5. 차단 확인: banExpiresAt != null && banExpiresAt.isAfter(now) → OAuth2AuthenticationException
6. CustomUserDetails(user) 반환
```

### 5.6 OAuth2LoginSuccessHandler

```
1. AT  = JwtUtil.generateAccessToken(userId, role)    (30분)
2. RT  = JwtUtil.generateRefreshToken(userId)         (7일)
3. Redis SET RT:{userId} {RT} EX 604800
4. HttpOnly 쿠키 Set-Cookie:
   name=refresh_token, httpOnly=true, path=/,
   maxAge=604800, secure/sameSite은 application.yml 프로파일 값
5. otcCode = UUID.randomUUID().toString()
   Redis SET OTC:{otcCode} {AT} EX 30
6. 302 redirect → {frontend.url}/auth/callback?code={otcCode}
```

### 5.7 AuthTokenService (Redis 키 관리)

```java
// Redis 키 체계
RT:{userId}    → Refresh Token       TTL 7일
OTC:{code}     → One-Time Code→AT   TTL 30초
BL:{jti}       → AT 블랙리스트       TTL = AT 잔여 시간 (AUTH-002에서 구현)

// OTC 교환 — 원자적 처리
String exchangeOtc(String code) {
    String at = redisTemplate.opsForValue().getAndDelete("OTC:" + code);
    // GETDEL (Redis 6.2+, Spring Data Redis 2.6+)
    if (at == null) throw new BusinessException(ErrorCode.OTC_INVALID);
    return at;
}
```

### 6.3 AuthStore (Zustand)

```typescript
interface AuthState {
  accessToken: string | null;
  userId: number | null;
  role: string | null;
  setAuth: (token: string) => void;   // jwtDecode(token)로 userId/role 추출
  clearAuth: () => void;
}
```

**페이지 새로고침 시 AT 소실:** AT는 의도적으로 메모리만 저장(CLAUDE.md 결정).
새로고침 후 첫 API 요청에서 401이 오면 Axios 인터셉터가 RT 쿠키로 자동 재발급한다.
재발급 실패 시 /login으로 이동. (401 인터셉터는 AUTH-003에서 구현)

### 6.4 Axios 인스턴스

```typescript
// lib/axios.ts
const api = axios.create({
  baseURL: process.env.NEXT_PUBLIC_API_URL,
  withCredentials: true,  // RT HttpOnly 쿠키 자동 전송
});

// 요청 인터셉터
api.interceptors.request.use((config) => {
  const { accessToken } = useAuthStore.getState();
  if (accessToken) config.headers.Authorization = `Bearer ${accessToken}`;
  config.headers['X-Requested-With'] = 'XMLHttpRequest';  // CSRF 방어
  return config;
});

// 응답 인터셉터: 401 처리는 AUTH-003에서 구현
```

### 6.5 useAuth 훅

```typescript
// hooks/useAuth.ts
export function useExchangeToken() {
  return useMutation({
    mutationFn: (code: string) =>
      api.post<ApiResponse<{ accessToken: string }>>('/api/auth/token', { code }),
    onSuccess: (res) => {
      useAuthStore.getState().setAuth(res.data.data.accessToken);
    },
  });
}
```

### 6.7 Callback 페이지 (`/auth/callback`)

```tsx
'use client'
const { mutateAsync: exchangeToken, isPending } = useExchangeToken();
const code = useSearchParams().get('code');

useEffect(() => {
  if (!code) { router.replace('/login'); return; }
  exchangeToken(code)
    .then(() => router.replace('/'))
    .catch(() => router.replace('/login?error=token_exchange_failed'));
}, [code]);
// 로딩 스피너 표시 (isPending)
```

### 6.8 next-auth v5 + middleware 역할

**AUTH-001에서의 역할:** 설정 파일(auth.ts) 및 middleware.ts 생성만.
`middleware.ts`는 이번 이슈에서 **pass-through stub** (모든 요청 통과).

```typescript
// middleware.ts — AUTH-001에서는 stub
export { auth as middleware } from '@/auth';
export const config = { matcher: [] }; // 아무 경로도 보호하지 않음
```

**향후 역할:** AUTH-002/003 이후, Zustand AT 메모리 방식과 next-auth 세션 방식의
공존 전략을 결정한 후 미들웨어 보호 라우트를 완성한다.
AT를 next-auth session에도 저장할지, 미들웨어는 쿠키 존재만 체크할지를 그 때 결정한다.

BE PR이 먼저 머지된 후 FE PR 머지 (BE 엔드포인트 선행 필요).
